# Firmware builds and releases

CI checks every PR and push to `master`. The firmware check uploads an MCUBoot
image, RTT ELF, and an application-only Nordic DFU ZIP built with
`mcuboot,ota-activation`. Download the PR artifact from its Actions run to test
it locally; the ZIP can be selected in Furu without copying a locally built file
from the computer. Actions artifacts are temporary and are not the in-app feed.

To make a tested PR build available in Furu's opt-in development channel,
create a **deliberate** development tag on that exact commit after reviewing the
PR checks and hardware risk. This publishes a GitHub prerelease. Do not tag
unreviewed commits or a firmware build whose trial/rollback behavior has not
been tested on the development board.

```bash
git fetch origin
commit=<reviewed-commit-sha>
version=<Cargo.toml-version>
git tag "v${version}-dev.${commit:0:7}" "$commit"
git push origin "v${version}-dev.${commit:0:7}"
```

For a release candidate, merge to `master`, update `Cargo.toml` to the intended
version in a reviewed PR, and tag the merged commit `vX.Y.Z-rc.N`. For a stable
release, use `vX.Y.Z`. The base `X.Y.Z` must match `Cargo.toml`; the suffix is a
distribution-channel label, while MCUBoot's numeric image version remains
`X.Y.Z`. The release workflow rejects a stable or RC tag that is not on
`master`, and rejects a development tag whose SHA suffix does not match its
commit. It uploads `kongle-<tag>-dfu.zip`, `SHA256SUMS`, and release notes to
GitHub Releases. Furu reads those published releases, including prereleases
only when its development channel is enabled.

The ZIP contains **only the application image**. It does not update the
bootloader or recovery image. All published images contain the opt-in OTA
receiver and request an MCUBoot test swap after validation. They do not mark
the trial image as confirmed: a reset may revert to the previous firmware.
Keep the debugger/recovery path ready when testing new images, especially on a
closed watch.

The first `v0.2.0` release uses a reviewed baseline summary in
`docs/release-notes/v0.2.0.md` because the pre-release history contains many
housekeeping commits. Later release notes are generated by
[git-cliff](https://git-cliff.org/) from commits since the previous stable tag.
Prefer concise `feat:`, `fix:`, and `docs:` PR titles or squash-commit subjects
so the notes describe user-visible changes. Preview the notes for a tag with:

```bash
devenv shell -- bash scripts/release-notes.sh vX.Y.Z /tmp/kongle-release-notes.md
```

The maintainer reviews the GitHub Release notes and verifies the ZIP with the
development watch before recommending a release to daily-driver users. Release
publication does not automatically confirm firmware on a watch.
